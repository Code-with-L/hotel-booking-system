## 2. Existing admin architecture (preserved)

M1–M3 shipped an authenticated operations area, not a mock:

- **Frontend** (`apps/web/src/pages/Admin/*.jsx`): Dashboard, Reservations, Rooms, Guests, Rates, Reports, Settings — plain Vite + React, no new design system; `AdminLayout.jsx` renders the staff sign-in gate, nav, top bar; `AdminUI.jsx` holds the dense admin primitives (`Stat`, `Panel`, `StatusBadge`, `Table`, `Toolbar`).
- **Backend** (`apps/api/src/modules/admin/routes.js` on `adminRouter`): dashboard, reservations list/detail/status-PATCH, rooms list/PATCH, guests list/detail, rates, reports (occupancy, monthly, reconciliation), settings, audit-log, desk payments. RBAC via `requireRole(...)` middleware per endpoint — server-side, not nav-hiding.
- **Engine (untouched in M4 except §5.4)**: PostgreSQL 16 + Prisma; `room_allocation` ledger; partial `EXCLUDE USING gist` overlapping-occupying constraint (`room_allocation_no_overlap`) as the hard arbiter; allocation-aware availability; PostgreSQL exclusion violations map to `409 ROOM_UNAVAILABLE`.
- **Audit**: `lib/audit` appends to `audit_log` inside the same transaction as the protected operation — an audit write failure aborts the operation (proven in M4 tests).

M4 extended these seams; no second admin area, no schema re-design, no redesign of the frontend.

## 3. Implemented functionality

### 3.1 Administrative dashboard
- Extended `GET /admin/dashboard` with operational facts derived from the ledger: `pendingCount`, `confirmedCount`, `cancelledLast30Days`, `paymentSummary` (succeeded/pending/failed counts + amounts), `outstandingMinor` (raw SQL `GREATEST(total - paid, 0)` over confirmed/in-house/checked-out reservations), plus existing totals (occupancy %, arrivals/departures today, revenue, availability by type, recent list).
- Dashboard UI: new "Needs action", "Confirmed" stat tiles; "Pending actions" and "Payments" panels (payments summary + link to Financials); existing layout and design tokens unchanged.
- Loading / error / empty states retained everywhere figures render.

### 3.2 Reservation management
- List rows now carry `paymentStatus` (`Paid|Partial|Unpaid` vs succeeded payments) and `totalPaidMinor`; the table shows a Paid column.
- Detail drawer (`GET /admin/reservations/:reference`) returns `breakdown` (nightly rate, subtotal, SC 10%, tourism levy 2%, VAT 16%, cancel fee, taxes-and-fees rollup) and `payments[]`; drawer renders the itemised quote with the same KV styling as the booking flow, plus per-reservation payment lines (provider/status/amount).
- Status workflow unchanged in shape; transitions now use **compare-and-swap** (`UPDATE reservation SET ... WHERE id=? AND status=<expected>` + row-count check) so two staff members cannot both confirm/cancel — exactly one wins, losers get `409 "Another staff member changed this reservation first."`. Audited in the same transaction (atomic).
- Search (`q` across reference/guest/room), filter by status and room type, sort — unchanged, still server-paginated.
- Expired holds remain visible as `Expired` (sweeper + 15-minute TTL, M1); check-in/check-out transitions enforce the state machine (`pending→confirmed→checked_in→checked_out`, any pre-completion state→`cancelled`); invalid transitions → `409`.
- Reservation history per room added (see 3.3).

### 3.3 Rooms & inventory
- `PATCH /admin/rooms/:number` — hard guard: setting `out_of_service` while any **occupying allocation** of kind `hold` **or** `reservation` overlaps the next 365 days → `409` listing the blocking reservation references. **No override exists.** Confirmed reservations are never silently invalidated by maintenance.
- New `GET /admin/rooms/:number/history` (receptionist+): allocation ledger rows for the unit (kind, state, dates, source reference, guest, total) with `Completed`/`In effect` derived labels (past vs future window) — ledger rows are raw history; nothing is rewritten.
- Rooms page: per-row **History** drawer (`.drawer--wide`, scrollable table) with maintenance-guard notice in the page note; allocation kind display (`Maintenance`/`Hold`/`Reservation`) + release/expire outcomes.
- Rate plans & pricing management: pre-existing (Rates page, manager+) — preserved unchanged in M4.
- Occupancy by date: pre-existing Reports (`occupancy`, `monthly`) — preserved.

### 3.4 Guest management
- Operational notes: `PATCH /admin/guests/:id` (staff-only, ≤800 chars) writes `guest.notes` **and** an `audit_log` entry (`guest.notes_updated`, before/after) in one transaction.
- Guests page: notes editor per expanded dossier (textarea + Save + audit-backed). Guest history (reservations, upcoming/cancelled) pre-existing — preserved. RBAC: guests cannot write notes; non-staff cannot read the endpoint at all.
- No new collection beyond pre-existing profile fields; no profiling, no export/download surface added. Data minimisation preserved.

### 3.5 Staff roles & permissions
See §7 matrix. Enforced in middleware (`requireRole`) on every endpoint — hiding nav is presentation only. Backend tests call the API directly as guest/receptionist/manager/admin (including negative paths). No new roles were introduced (three ship: `receptionist`, `manager`, `admin`; plus unauthenticated and guest).

### 3.6 Check-in / check-out
State machine enforced server-side with CAS transitions; duplicate check-ins rejected (`409`); `checked_in` stamps `checkedInAt`, `checked_out` stamps `checkedOutAt`; transitions write audit rows. Concurrent-confirm test: 5 parallel PATCHes → exactly one `200`, four `409`.

### 3.7 Financial visibility
- New `GET /admin/reports/financial-summary` (manager+): collected (succeeded count+amount), pending value/count, failed count, refunds (from `payment_attempt.status='refunded'`), cancellation fees (sum `cancelFeeMinor` over cancelled), **outstanding** balances (per-reservation list + total, `GREATEST(total − succeeded, 0) > 0` over confirmed/in-house/checked-out), last 10 payments. All figures computed from real `payment`/`reservation` rows; currency KES; **no synthetic transactions**; M-Pesa appears only when configured (else `MPESA_NOT_CONFIGURED` pattern untouched).
- New **Financials** page (`/admin/financials`, nav "Financials", `Banknote` icon): stat strip + outstanding-balances table + recent payments table; links to Reservations. Existing styling; `EmptyRow` states.
- Reservation list shows Paid badge per row; desk settlement flow (pre-existing) unchanged; reports reconciliation (pre-existing) unchanged.

### 3.8 Audit trail
- Append-only; `admin` role only on `GET /admin/audit-log`; every M4 write path emits rows (`reservation.confirmed/checked_in/checked_out/cancelled`, `guest.notes_updated`, `room.*` via existing room audit, `financial` via existing paths) with actor, entity, before/after JSON, IP, timestamp.
- **Audit-failure handling is enforced, not aspirational:** all protected writes happen inside one `prisma.$transaction` including the `audit_log` insert; test `audit failure blocks the protected operation` renames `audit_log` mid-flight and asserts the cancellation returns 5xx **and the reservation is untouched**.

### 3.9 Concurrency hardening (engine-adjacent, documented in §5.4)
- `findFreeRooms` now takes `SELECT ... FOR UPDATE` on the candidate room set in ascending `id` (identical lock order in every transaction → no self-deadlock; serialises contenders on the same room type before the exclusion constraint is ever needed). Combined with jittered backoff between `ROOM_UNAVAILABLE` retries (§5.4), the M1 "8 parallel bookings for 5 rooms" baseline is deterministic rather than luck-based.

## 5. Database changes

### 5.1 Schema
**None.** No migrations added, no columns dropped, no constraint altered. `room_allocation`, `reservation`, `payment`, `guest`, `audit_log` used as-is.

### 5.2 Runtime locking (not a schema change)
`SELECT ... FOR UPDATE` on candidate rooms inside the booking transaction (see 3.9). Ordered ascending; covers only the 5–9 candidate rows; held for milliseconds.

### 5.3 Dev-DB data cleanup (documented, with compensation)
11 synthetic rows in the **development** database (`guest` table, `example.com` race-probe artifacts from a pre-M4 concurrency probe, all with **zero reservations**; `RaceN Test` / `raceN.<epoch>@example.com`, created 2026-11-10 23:02–23:04) were removed after exporting them to `race-guests-backup.json`. Deletion statement and verification: `DELETE … WHERE email ~ '^race[0-9]+\.[0-9]+@example\.com$' AND firstName ~ '^Race[0-9]+$' AND lastName = 'Test' AND NOT EXISTS (SELECT 1 FROM reservation r WHERE r.guestId = g.id)` → `DELETE 11`, post-count 0. **No fixture business data was altered.** Not applied to any production database.

### 5.4 Engine retry backoff (not schema)
`createReservationTx` now waits `40ms×(attempt+1) + rand(60ms)` between allocation-conflict retries (still max 6 attempts; `ROOM_UNAVAILABLE` only). Purely defensive jitter; no business-rule change.

## 7. Security findings

- **Maintenance guard leak closed:** previously `out_of_service` interacts with allocations implicitly; M4 makes it explicit and total (409, blocking refs listed). No override, no silent displacement of confirmed stays.
- **Double-action race closed:** status PATCH is compare-and-swap; audit inside the same transaction; audit failure → operation aborts (5xx, zero side effects) — covered by a dedicated test that drops `audit_log` and observes an untouched reservation.
- **Data minimisation kept:** guest-notes endpoint is staff-only, length-capped, and writes audit metadata (not a dump of PII into logs).
- **Financial integrity:** figures are read-only aggregates; refunds remain a recorded, off-system money movement (never fake); M-Pesa still 503 `MPESA_NOT_CONFIGURED` without credentials — nothing in M4 claims otherwise.
- **Un-authenticated access:** 401 on all admin endpoints without a session; 403 with a guest session; 403 with receptionist on manager endpoints; all verified in tests.
- No new secrets introduced; `.env.example` unchanged (names only). `npm audit` status unchanged from M2-D (3 high, dev-only Prisma CLI chain, accepted, re-check at M7).
- Rate limiting unchanged (300 req/15 min per IP; webhooks/health exempt). Session model unchanged.

**No critical or high findings introduced by M4.** Residuals carried: dev-only default passwords must not reach production (M2-D guard exists), no CSRF token beyond SameSite=Lax+JSON (accepted, M2), KRA/eTIMS unsigned (pre-existing, owner-gated).

**M1 baseline regression & fix (honest account):** after M4's first full-suite run, `booking.test.js › 8 parallel bookings for 5 rooms` failed with 4×201 instead of 5×201 in ~2/3 of runs. Root-caused: vitest's file execution order varies by run; when `m4.test.js` ran first it left one signature-retreat room `out_of_service` (maintenance-guard test) and nothing restored it, shrinking signature-retreat to 4 active rooms (`S03`) for subsequent files. **It was not an engine defect — the 4 wins were correct given the fixture damage.** Fix: the M4 guard test now restores the room's `status`/`notes` in a `finally` block, and the allocation layer was additionally serialised (`FOR UPDATE` + backoff, §3.9/5.2/5.4) so a room cannot be stranded by speculation-losing retries. Verified: 8/8 consecutive clean 31/31 runs after the fix. The M1 test itself was **not** modified.

## 10. Remaining limitations

- No multi-property/multi-unit tenancy; single-property model.
- No housekeeping statuses beyond Vacant clean / Occupied / Out of service; no room moves history beyond the ledger.
- No booking edit-in-place (dates/rooms) — cancel + rebook remains the supported flow (D-027).
- Hold TTL 15 minutes; no long-term tentative holds.
- Guests page shows full list (no server-side search yet for >100 records; fine at 28-room scale).
- Financial summary trusts recorded money movements only; cash/card rails outside the system are invisible to it (by design).
- Admin area has no dark mode (by design, D-017) and no mobile-specific IA beyond stacking (tablet OK, phone usable; native-admin UX not a goal).
