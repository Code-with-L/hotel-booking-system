## 2. Hosting architecture (decision)

**Shape:** 1 static-SPA container (nginx, TLS termination + CSP) + 1 stateless Node API container + 1 PostgreSQL 16 instance + in-container background sweepers (hold expiry, stale-payment requery, eTIMS invoice retry, arrival reminders — all in-process, 60s interval). No Kubernetes, no microservices.

**Decision:** single VPS/app host in an EU region closest to Kenya (Fly.io/Railway/Render-class or Hetzner/Linode/DO) with **managed PostgreSQL 16** (Neon/Render/RDS-class) providing automated backups + PITR. Local verification uses the committed `docker-compose.staging.yml` on this dev host (container PG with a persistent named volume).

**Options evaluated:** managed host+PG (≈$5–20/mo, lowest ops) vs full VPS (more control, more ops) vs Vercel+Neon (splits SPA/API across platforms — rejected: second domain, second trust boundary, CORS/cookie complexity). Chosen option minimizes ops while keeping the topology identical to what is rehearsed locally. Full trade-off table and local commands: `docs/STAGING.md` §1–3.

## 3. Staging environment (what was actually built and verified)

`docker-compose.staging.yml` — isolated compose project `stillhouse-staging`:

| Component | Detail |
|---|---|
| `stillhouse-staging-db` | postgres:16-alpine, container `stillhouse-staging-db`, **persistent named volume** (`stillhouse_staging_data`), loopback-only host access `127.0.0.1:5434`, healthcheck, healthy |
| `stillhouse-staging-api-1` | production image (`apps/api/Dockerfile`), `NODE_ENV=production`, cookie-secure, `TRUST_PROXY=1`, integrations all disabled (503/skipped — never fake), `/api/v1/ready` healthy, non-root user |
| `stillhouse-staging-web-1` | production image with **staging TLS vhost baked in** (`apps/web/Dockerfile` build-arg `NGINX_CONF=nginx.staging.conf` — no stale 9p bind-mounts into nginx), TLS on 443, HTTP→HTTPS 301, `/healthz` on 80 for container probes, CSP/HSTS/headers, non-root nginx ports |

**TLS:** self-signed CA cert with SAN `staging.stillhouse.local, localhost, 127.0.0.1`, generated locally (OpenSSL via Docker), **gitignored** (`deploy/certs/`), verified from the host with `--cacert` (homepage 200, availability 200, ready 200, admin 200). Browsers will warn until a real CA issues a cert for a real domain; that is the owner's action (§15).

**Seed:** staging DB seeded with the dev fixture set (34 fake reservations, fake guests on example.com domains, demo staff accounts with owner-held passwords) — explicitly labelled fixtures, loopback-only, zero overlap with development (`stillhouse-db-test`) or production (does not exist).

**Environment separation:** development (`stillhouse-db` :5432), isolated test (`stillhouse-db-test` tmpfs :5433, wiped per run), staging (`stillhouse-staging-db` :5434, persistent). Staging never shares a database with development or production.

**Notable operational incident (recorded honestly):** initial staging bring-up used compose's default project name, which made the dev DB container get recreated as a "project orphan" and one dev container was briefly removed by an accidental `docker compose down`. **No data was lost** — the dev database lives on the persistent `stillhouse_db_data` volume; verified intact (42 reservations, 28 rooms, 41 allocations). The staging stack was then brought up under its own isolated project name (`-p stillhouse-staging`) and the dev stack restored (`docker compose up -d db db_test`; data verified). This is exactly why staging is now namespaced and why `.env.staging`/certs are gitignored.

## 6. Security configuration

- **Boot-time production guard** (M2-D) re-verified live: starting the API image with `NODE_ENV=production` and no `SESSION_SECRET` exits non-zero with the explicit message (evidence: `m6-rehearsal/failed-deploy.json`).
- **Cookies:** `Secure; HttpOnly; SameSite=Lax`, `COOKIE_SECURE=true` in staging env; boot refuses otherwise.
- **CORS:** single allowlisted origin (`WEB_ORIGIN`), credentialed.
- **HSTS** on (`max-age=31536000; includeSubDomains`); CSP: `default-src 'self'; img-src 'self' data: https:; style-src 'self' 'unsafe-inline'; font-src 'self'; script-src 'self'` (self-hosted fonts). `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` — all in nginx vhost; replicated in the base `apps/web/nginx.conf` (self-hosted fonts since M5).
- **Network exposure:** staging ports bound to 127.0.0.1; db loopback-only; API internal-only (no host port); web terminates TLS.
- **Self-signed CA + certs are gitignored** (`deploy/certs/`); `.env.staging` gitignored; `.env.staging.example` holds names only; `.dockerignore` excludes `.env*` and `dist`.
- **Rate limiting / auth / audit** unchanged from M2–M5 and re-verified by suite.
- **No staging credentials are in this repository or this report.**

## 10. Rollback rehearsal (executed, not written)

- **Application rollback:** `docker restart` on `stillhouse-staging-api-1` and `stillhouse-staging-web-1` → `/ready` returned 200 after ≤10s and HTTPS `/healthz` 200; booking state intact (no data touched).
- **DB interruption:** `docker stop stillhouse-staging-db` → `GET /api/v1/ready` returns **503** (not 500, not a hang); `docker start` → 200 within ~30s; API process never needed restart.
- **Boot guard / failed deploy:** image started with missing `SESSION_SECRET` → non-zero exit with explicit message → deploy pipeline halts before traffic shift (this is the desired behavior; previous deployment keeps running).
- **Image rollback semantics:** app rollback = redeploy previous image tag (additive migrations need no DB rollback); DB rollback = restore-from-backup (drill verified, above).
