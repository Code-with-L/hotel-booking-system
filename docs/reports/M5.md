## 3. M-Pesa Daraja implementation and verification

### 3.1 What changed
- **OAuth token lifecycle** — `lib/mpesa.js` now caches the Daraja access token (module-level, ~50 min TTL) with single-flight refresh; concurrent callers share one in-flight token request; provider-declared `expires_in` is respected with a 30s safety margin. Transport failures (abort/DNS/socket) and OAuth failures map to truthful `502 MPESA_UPSTREAM_ERROR` — never a 500, never a fake success. Unconfigured credentials still yield `503 MPESA_NOT_CONFIGURED` (untouched).
- **Terminal-state idempotency** — the webhook now treats `succeeded|failed|refunded|partially_refunded` as terminal and returns `200` without touching the ledger; a **success callback against a settled-failed payment is logged as an anomaly** (`logger.error` with reference metadata) and never flips state — manual reconciliation required.
- **Duplicated-failure protection** — a replayed failing callback produces exactly one `payment_attempt` row (previously a second identical attempt could be appended).
- STK Push/Query/amount-verification/idempotency/IP-allowlist/requery sweeper from M2 — unchanged and still covered by their tests.

### 3.2 Verification (no live provider)
- New `tests/m5.test.js` (14 tests): token cache reuse across calls (one OAuth request for two pushes); token re-auth after expiry (`Date.now` advanced); OAuth 401 → 502 `MPESA_UPSTREAM_ERROR`; transport failure → 502; terminal-state replay (one failed attempt, no double-release); corrupting success callback against a settled-failed payment → no flip; financial-health endpoint RBAC + values; eTIMS idempotency + retry (mock provider); arrival reminder dedupe + HTML escaping; payment-health anomaly detection.
- **API suite: 45/45** (31 inherited + 14 M5), 2 consecutive full runs + rehearsal run.
- **Not live-verified**: a real Daraja sandbox transaction has never run — credentials are owner-gated (§13). What is verified is request shape, callback verification, idempotency, replay semantics, failure mapping, and the token lifecycle — all against a mocked HTTP boundary.
- Unconfigured behavior verified in tests (503, never a fake payment).

### 3.3 Classification
Daraja integration: **implemented, mock-tested, awaiting owner credentials**. Token lifecycle: **implemented and verified (mocked)**. Live verification: **not performed — owner action required** (`docs/ACTIVATE_MPESA.md`).

## 5. Payment reconciliation and financial consistency

### 5.1 New reconciliation report
`GET /admin/reports/payment-health` (manager+) — read-only, computed over the ledger with minor-unit integers:
`duplicate_provider_transactions`, `amount_mismatches` (attempt vs payment), `overpaid_reservations`, `cancelled_with_outstanding_payment` (captured, not refunded), `stale_pending_payments` (>45 min), `failed_payments_last_30d`, `invoices_failed`, `invoices_pending_stale`, `succeeded_sum_mismatch` (attempts vs payments totals), plus `payments_without_reservation` (always 0 — FK enforced, reported honestly). Each finding: severity, count, sample references, remediation hint. Never mutates the ledger.
- Financials page: read-only "Payment health" panel (findings with severity badges, counts and one-line remediation; empty state when clean).
- Test coverage: clean settled booking → `healthy: true`, zero findings; crafted anomalies (amount mismatch, stale pending mpesa payment, cancelled-with-capture, forced `failed` invoice) → each detected by ID; totals cross-checked (`succeededMinor` == attempts sum); RBAC (anon 401, guest 403, receptionist 403, manager 200).

### 5.2 Financial integrity of the pipeline
No financial rule was modified. Cancellation fees still recorded at cancellation (`cancelFeeMinor` from rate-plan policy); desk settlement still full-balance-only and idempotent; refunds remain manual, off-system money movement recorded in `payment_attempt` (never simulated, capped at the paid amount); reconciliation now *surfaces* inconsistencies instead of editing them. Cross-endpoint consistency is what `payment-health` measures; the automated test suite and the release rehearsal both confirm a coherent ledger end-to-end.

### 5.3 Classification
Reconciliation report: **implemented and verified** (mocked/crafted data paths). Financial consistency enforcement: **implemented (read-only detection), no auto-correction by design**. Outstanding/feed integrity: **tested via rehearsal** (§9).

### 6.2 What M5 added

- **Arrival reminder sweeper**: runs in-process every 60s; selects tomorrow's `confirmed` check-ins; sends at most one reminder per reference (dedupeKey) — test proves template render + escaping (`<Ada>` → `&lt;Ada&gt;`) + idempotency.
- No marketing, no tracking, no newsletters added.
